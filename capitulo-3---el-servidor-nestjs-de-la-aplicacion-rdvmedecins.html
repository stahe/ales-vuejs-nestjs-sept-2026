    4. Capítulo 3 - El servidor [NestJS] de la aplicación [RdvMedecins]

    Este capítulo detalla, archivo por archivo, el contenido de la carpeta [rdvmedecins-nestjs-server] incluida con este documento. Sigue el mismo formato utilizado a lo largo de todo este curso: el código fuente, numerado línea por línea, seguido de una sección titulada «Comentemos este código», que explica las líneas que requieren mayor aclaración. Cada carpeta de proyecto contiene además su propio archivo README.md, que incluye una versión resumida de estas explicaciones.

    4.1. La base de datos

La única novedad, introducida por la etapa de «autenticación» de esta adaptación: la tabla [users].

-- Base de datos [dbrdvmedecins] - MySQL 8

-- Este script reproduce EXACTAMENTE el esquema relacional del documento original
-- (2014, Spring 4 / Spring Data / MySQL 5): mismas tablas, mismas columnas,
-- mismas claves externas, misma restricción de unicidad. Solo el motor de base de datos

 CREATE TABLE clients (
   id         INT AUTO_INCREMENT PRIMARY KEY,

   last_name  VARCHAR(20) NOT NULL,
   first_name VARCHAR(20) NOT NULL
 );

 CREATE TABLE slots (
   id           INT AUTO_INCREMENT PRIMARY KEY,
   version      INT NOT NULL DEFAULT 0,

   end_hour     INT NOT NULL,
   end_minute   INT NOT NULL,

 );

 CREATE TABLE appointments (
   id         INT AUTO_INCREMENT PRIMARY KEY,
   version    INT NOT NULL DEFAULT 0,
   day        DATE NOT NULL,
   slot_id    INT NOT NULL,
   client_id  INT NOT NULL,
   CONSTRAINT fk_appointments_slot   FOREIGN KEY (slot_id)   REFERENCES slots(id),
   CONSTRAINT fk_appointments_client FOREIGN KEY (client_id) REFERENCES clients(id),
   CONSTRAINT unq1_appointments UNIQUE (day, slot_id)
 );

 CREATE TABLE users (

   version  INT NOT NULL DEFAULT 0,
   login    VARCHAR(30) NOT NULL UNIQUE,
   password VARCHAR(100) NOT NULL,

    • líneas 20–24: [DROP TABLE IF EXISTS …] : el script parte de una base de datos vacía en cada ejecución, siguiendo el orden inverso de las dependencias (comenzando por `appointments`, que referencia a `[slots]` y a `clients`, hasta llegar a `users`, a la que nadie referencia): [MySQL] se negaría a eliminar una tabla que todavía está referenciada por una clave externa;
    • línea 48: [doctor_id INT NOT NULL], luego línea 53: [CONSTRAINT fk_slots_doctor FOREIGN KEY …] : un horario siempre pertenece a un médico;
    • línea 64: [CONSTRAINT unq1_appointments UNIQUE (day, slot_id)] : la regla de negocio central de la aplicación: un mismo horario en un mismo día solo puede reservarse una vez. Es esta restricción, y únicamente ella, la que impide una cita duplicada; ni el validador ni la capa de lógica de negocio la vuelven a comprobar explícitamente (véase más adelante, addAppointment);
    • líneas 67–74: [CREATE TABLE users (…)] : la tabla agregada en esta etapa. `login` es UNIQUE (dos usuarios no pueden compartir el mismo identificador de inicio de sesión); `password` almacena una contraseña cifrada mediante hash con bcrypt (nunca en texto plano); role es 'ADMIN' o 'USER', una simple columna de texto, mientras que el documento original utilizaba tres tablas (users, roles, users_roles) para permitir varios roles por usuario. Dado que esta aplicación solo requiere dos roles mutuamente excluyentes, la relación muchos a muchos original habría sido excesiva;
    • líneas 91–93: [INSERT INTO users …] : dos cuentas de demostración, admin/admin (rol ADMIN) y user/user (rol USER), con sus contraseñas ya cifradas con bcrypt (10 rondas de salt), nunca en texto plano, ni siquiera en este script de demostración.

    El servidor sigue la estructura por capas del proyecto original:

    Cada capa se comunica únicamente con la capa inmediatamente a su derecha, [5-8]: así, el controlador [5] nunca se comunica directamente con la capa [7], por ejemplo.     4.3. Las entidades [TypeORM] (src/entities/)

    Las entidades son las clases que representan las filas de las tablas de la base de datos como objetos TypeScript; son el equivalente directo de las entidades JPA del proyecto original (paquete rdvmedecins.entities).

      import { [PrimaryGeneratedColumn], [VersionColumn] } from 'typeorm';

  export abstract class AbstractEntity {
    @PrimaryGeneratedColumn()
    id: number;

    @VersionColumn()
    version: number;
  }

    Comentemos este código:

    • línea 4: [@PrimaryGeneratedColumn()] : declara una clave primaria autoincremental mediante el SGBD, el equivalente exacto de @Id + @GeneratedValue(strategy = GenerationType.AUTO) en JPA;
    • Línea 7: [@VersionColumn()] : [TypeORM]’s mecanismo nativo de bloqueo optimista: [TypeORM] incrementa automáticamente esta columna con cada modificación y genera un error si se intenta guardar una entidad cuya versión ya no coincide con la de la base de datos (alguien más la modificó entretanto); es el equivalente exacto de @Version en JPA/Hibernate;
    • Línea 3: [export abstract class AbstractEntity {] : esta clase no está decorada con [@Entity]: no corresponde a ninguna tabla por sí sola. [TypeORM] denomina a esta técnica «Concrete Table Inheritance»: cada subclase decorada con [@Entity] obtiene su propia tabla, con todas las columnas heredadas; es el equivalente exacto de @MappedSuperclass en JPA.

      import { [Column], [Entity], [JoinColumn], [ManyToOne], [RelationId] } from 'typeorm';
  import { AbstractEntity } from './abstract.entity';
  import { Doctor } from './doctor.entity';

  @Entity({ name: 'slots' })
  export class Slot extends AbstractEntity {
    @Column({ name: 'start_hour' }) startHour: number;
    @Column({ name: 'start_minute' }) startMinute: number;
    @Column({ name: 'end_hour' }) endHour: number;
   @Column({ name: 'end_minute' }) endMinute: number;

   @ManyToOne(() => Doctor, (doctor) => doctor.slots)
   @JoinColumn({ name: 'doctor_id' })
   doctor: Doctor;

   @RelationId((slot: Slot) => slot.doctor)
   doctorId: number;
 }

    Analicemos este código:

    • líneas 7–10: [@Column({ name: 'start_hour' }) startHour: number; …]: los cuatro límites de tiempo del horario de la cita (hora y minuto de inicio y de fin), cuatro enteros simples, cada uno asignado a su columna en snake_case (start_hour, start_minute, end_hour, end_minute);
    • línea 12: [@ManyToOne(() => Doctor, (doctor) => doctor.slots)] : varios horarios pertenecen al mismo médico. De forma predeterminada, [TypeORM] no carga la relación «doctor» al leer un horario (comportamiento «lazy» predeterminado): debe solicitarla explícitamente (opción de relación: [...] en una consulta), exactamente como FetchType.LAZY exigía, del lado de JPA, un `left join fetch` explícito en la consulta JPQL para recuperar al médico;
    • línea 13: [@JoinColumn({ name: 'doctor_id' })] : especifica el nombre de la columna de la clave externa en la tabla [slots];
    • línea 16: [@RelationId((slot: Slot) => slot.doctor)] : el equivalente exacto e idiomático, del lado de [TypeORM], del campo de solo lectura idMedecin del proyecto original ([@Column](name = "id_medecin", insertable = false, updatable = false)): expone directamente el valor de la clave externa, sin necesidad de cargar toda la entidad [Doctor], lo que resulta útil para construir respuestas JSON ligeras (véase más adelante, la capa web).

    Nota: Un campo [@RelationId] es una columna virtual, calculada a posteriori por [TypeORM]; no es una verdadera columna SQL que pueda usarse en una cláusula WHERE de un «query builder» (véase más adelante, [SlotRepository]). Se utiliza únicamente para recuperar el valor de la clave externa una vez cargada la entidad.

      import { [Column], [Entity], [JoinColumn], [ManyToOne], [RelationId], [Unique] } from 'typeorm';
  import { AbstractEntity } from './abstract.entity';
  import { Client } from './client.entity';
  import { Slot } from './slot.entity';

  @Entity({ name: 'appointments' })
  @Unique('unq1_appointments', ['day', 'slot'])
  export class Appointment extends AbstractEntity {
    @Column({ type: 'date' })
   day: string;

   @ManyToOne(() => Client)
   @JoinColumn({ name: 'client_id' })
   client: Client;

   @ManyToOne(() => Slot)
   @JoinColumn({ name: 'slot_id' })
   slot: Slot;

   @RelationId((appointment: Appointment) => appointment.client)
   clientId: number;

   @RelationId((appointment: Appointment) => appointment.slot)
   slotId: number;
 }

    Comentemos este código:

    • Línea 7: [@Unique('unq1_appointments', ['day', 'slot'])] : hace referencia, del lado de [TypeORM], a la restricción SQL del script de la base de datos. Observe que aquí se hace referencia al nombre de la relación («slot»), no al campo [@RelationId] («slotId»); este último es una columna virtual, que [TypeORM] no acepta en una restricción @Unique. [TypeORM] se encarga de asignar 'slot' a su columna real de clave externa (slot_id);
    • línea 9: [@Column({ type: 'date' })] : tipo 'date' (no 'datetime'): solo se conserva el día, no la hora, exactamente como especificaba TemporalType.DATE del lado de JPA;
    • líneas 12–18: [@ManyToOne(...) / @JoinColumn(...)] : dos relaciones, con [Client] y con [Slot], siguiendo el mismo principio que [slot.entity.ts];
    • líneas 20–24: [@RelationId(...)] : los equivalentes de solo lectura de los campos idClient/idCreneau del proyecto original (mismo mecanismo que Slot.doctorId; véase más arriba).

    4.5. La capa DAO (src/repositories/)

    La capa DAO (Data Access Object) es la única parte del proyecto que se comunica directamente con TypeORM/MySQL; equivale a las interfaces de Spring Data del proyecto original (paquete rdvmedecins.repositories).

    La diferencia más importante que hay que comprender entre Spring Data y [TypeORM]: Con Spring Data, bastaba con declarar una interfaz (extends CrudRepository<...>) para obtener automáticamente los métodos básicos (findAll, findOne, save, delete, etc.); Spring mismo generaba, al iniciar, una clase que la implementaba. Con [TypeORM], no existe la generación automática de una implementación a partir de una interfaz: se inyecta directamente el Repository<Entity> genérico que provee [TypeORM] (mediante [@InjectRepository]) y se escriben uno mismo los métodos que se desea exponer, apoyándose en los métodos predefinidos de este Repository o usando el query builder para consultas más específicas.

    4.8. Autenticación (src/auth/)

    Esta sección documenta la incorporación, en esta etapa del curso, de la autenticación basada en tokens (JWT) y del control de acceso basado en roles (ADMIN/USER), el equivalente funcional de la capa Spring Security del documento original, reescrita con herramientas estándar del ecosistema [NestJS]: [@nestjs/passport] y @nestjs/jwt.

    Dos diferencias intencionales con el proyecto original, documentadas aquí de una vez por todas:

    1. JWT en lugar de HTTP Basic. El proyecto Spring original enviaba el encabezado Authorization: Basic <login:password en Base64> con cada solicitud: la contraseña (codificada, no cifrada) se transmitía por la red en cada llamada. Este port utiliza en su lugar un token: JWT (JSON Web Token). La contraseña se presenta una sola vez, al iniciar sesión (POST /login); el servidor devuelve entonces un token firmado, que el cliente incluye después en cada solicitud posterior (encabezado Authorization: Bearer <token>). Esta es la práctica actual para este tipo de API, como ya se mencionó en la conclusión del capítulo anterior.
    2. Un rol por usuario, una sola columna de base de datos, en lugar de la relación de muchos a muchos (users/roles/users_roles) del proyecto original; véase user.entity.ts más arriba.

    Un punto de arquitectura que conviene entender antes de leer el código que sigue: cuando un guardia rechaza una solicitud (401 Unauthorized, 403 Forbidden), la respuesta nunca pasa por el envoltorio habitual [ServerResponse]<T> ({ status, data }): [NestJS] responde directamente en su formato JSON nativo, { statusCode, message, error }. Es una decisión deliberada: los errores de seguridad se tratan antes de entrar al controlador (mediante un guardia), mientras que [ServerResponse]<T> lo genera el controlador para los errores de negocio (recurso no encontrado, fecha no válida, etc.). Por lo tanto, el cliente [Vue.js] debe distinguir entre estos dos tipos de respuestas de error (véase el capítulo siguiente, auth.interceptor.ts).

       context.getClass(),

  @Injectable()
 export class AuthService {
   constructor(
     private readonly userRepository: UserRepository,
     private readonly jwtService: JwtService,
   ) {}

   async validateUser(login: string, password: string): Promise<User | null> {
     const user = await this.userRepository.findByLogin(login);
     if (user === null) {
       return null;
     }
     const passwordCorrect = await bcrypt.compare(password, user.password);
     return passwordCorrect ? user : null;
   }

   login(user: User): LoginResult {
     const payload: JwtPayload = { sub: user.id, login: user.login, role: user.role };
     return {
       accessToken: this.jwtService.sign(payload),
       login: user.login,
       name: user.name,
       role: user.role,
     };
   }
 }

    Comentemos este código:

    • línea 10: [export class AuthService {] — conceptualmente equivalente a la clase AppUserDetailsService del proyecto Spring Security original, combinada aquí con la generación del token;
    • línea 16: [async validateUser(login: string, password: string): Promise<User | null> {] — verifica que exista un usuario con ese login y que la contraseña proporcionada coincida; devuelve el usuario si todo es correcto y null en caso contrario;
    • línea 21: [const passwordCorrect = await bcrypt.compare(password, user.password);] — bcrypt.compare() aplica un hash a la contraseña usando el mismo salt que el almacenado en user.[password], y luego compara los dos resultados; la contraseña almacenada nunca se descifra (el hash no es reversible);

    • línea 28: [accessToken: this.jwtService.sign(payload),] — jwtService.sign() firma el payload con la clave secreta y el tiempo de expiración configurados en auth.module.ts (JwtModule.register).

    • líneas 10–15: [app.useGlobalPipes(new ValidationPipe({ transform: true, whitelist: true }));] — verifica automáticamente, en cada solicitud entrante, que el cuerpo JSON se ajuste al formato esperado (véanse las clases decoradas con class-validator); `transform: true` convierte automáticamente los tipos (p. ej., la cadena "3" → el número 3), y `whitelist: true` elimina de los datos recibidos los campos que no están declarados en el `DTO`;
    • Línea 16: [const port = process.env.PORT ? parseInt(process.env.PORT, 10) : 8080;] — el puerto por defecto, 8080, es el mismo que el del servidor Spring Boot original.

    4.10. Verificación de extremo a extremo

    Esta etapa se verificó mediante unos diez escenarios con curl contra una copia de prueba del servidor (base de datos en memoria, prepoblada con las dos cuentas admin/admin y user/user):

    • POST /login con las credenciales correctas devuelve correctamente { "status": 0, "data": { "accessToken": "...", "login": "admin", "name": "Administrator", "role": "ADMIN" } };
    • POST /login con una contraseña incorrecta devuelve 401 Unauthorized (forma JSON nativa de [NestJS], no el envoltorio [ServerResponse]<T>);
    • GET /getAllDoctors sin encabezado Authorization devuelve una respuesta 401 Unauthorized;
    • GET /getAllDoctors con un token JWT válido (admin o user) devuelve normalmente la lista de médicos en el envoltorio [ServerResponse]<T> habitual;
    • POST /addAppointment con el token de admin reserva normalmente una franja horaria disponible;
    • POST /addAppointment con el token de user devuelve un error 403 Forbidden, con el mensaje de que el rol [USER] no permite esta acción (rol requerido: ADMIN);
    • POST /deleteAppointment se comporta de forma simétrica a /addAppointment según el rol del token presentado.
