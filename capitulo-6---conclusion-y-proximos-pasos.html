    7. Capítulo 6 - Conclusión y próximos pasos

    7.1. Lo que se ha construido

    Este documento ha adaptado el núcleo funcional y la autenticación de la aplicación [RdvMedecins] del documento original de 2014 a las tecnologías actuales:

    • un servidor [NestJS] completo (entidades [TypeORM], DAO, capa de negocio, capa web) que expone las mismas 11 rutas de negocio (JSON) que el servidor Spring 4 original, en el mismo puerto (8080), todas ahora protegidas por un token (JWT);
    • una capa de autenticación ([@nestjs/passport] + [@nestjs/jwt]): autenticación por usuario y contraseña (POST /login), un token firmado que se presenta con cada solicitud posterior y control de acceso basado en roles ([@Roles]('ADMIN') + [RolesGuard]) en las dos rutas que modifican datos;
    • un cliente [Vue.js] (Composition API, setup script) que ofrece la misma funcionalidad que el cliente AngularJS 1.x original (seleccionar un médico y una fecha, ver la agenda, reservar y cancelar una cita), complementada con una pantalla de inicio de sesión, una sesión persistente (localStorage), una interfaz Bootstrap que se adapta al rol del usuario con sesión iniciada (botones de reserva ocultos para un rol específico USER) y la posibilidad de cambiar la interfaz entre francés e inglés ([vue-i18n]).

    El núcleo de la base de datos no ha cambiado (las mismas tablas [doctors/clients/slots/appointments], las mismas restricciones), salvo por la adición de la tabla [users]; tampoco ha cambiado la arquitectura general en capas: solo se han actualizado las herramientas que la implementan.

    Hay dos diferencias intencionales con respecto al proceso de autenticación del documento original, documentadas en detalle en el Capítulo 3: un token JWT en lugar del encabezado HTTP Basic enviado con cada solicitud, y una única columna [role] por usuario en lugar de una relación de varios a varios entre tres tablas. Una tercera diferencia, esta vez funcional, se eligió deliberadamente para este port: el rol USER ahora puede ver las agendas (solo lectura), mientras que en el original solo servía para ilustrar una denegación total de acceso.

    7.2. Lo que queda fuera del alcance o pendiente de portar

    Además de lo anterior, el documento original abordaba dos temas adicionales, uno de los cuales ya se ha tratado, otro se ha dejado fuera deliberadamente y el tercero se ha aplazado a una etapa posterior:

    7.2.1. Internacionalización francés/inglés: tratada en este documento

    El documento original proponía cambiar la interfaz entre francés e inglés mediante la biblioteca [angular-translate]. Este port implementa esta funcionalidad con su equivalente en el ecosistema actual de [Vue.js], [vue-i18n] (cuyos diccionarios fr.json/en.json se cargan por HTTP desde la carpeta [public/i18n/] mediante una pequeña función de carga escrita para este port, ya que no existe un plugin HTTP oficial equivalente al que se usó del lado de React); véase el Capítulo 5. Como [angular-translate] antes que él, [vue-i18n] permite cambiar de idioma sobre la marcha, sin recargar la página, un comportamiento fiel al del documento original.

    7.2.2. El modo “debug” del cliente: excluido deliberadamente del alcance

    El documento original incluía un modo de visualización técnico, activable desde la interfaz, que daba acceso al modelo sin procesar ($scope de AngularJS 1.x) de la vista actual, una funcionalidad útil en 2014, cuando las herramientas de desarrollo disponibles para inspeccionar una aplicación AngularJS eran todavía limitadas. Este port no la recrea: las herramientas de desarrollo actuales de [Vue.js] ([Vue.js] DevTools, la extensión oficial del navegador) ofrecen ahora, fuera de la propia aplicación, una inspección mucho más completa de los componentes, su estado y sus props que la que ofrecería un panel de depuración propio reintegrado en la interfaz. Añadir un panel así equivaldría a crear una versión inferior de una herramienta que ya proporciona el ecosistema; por lo tanto, esta decisión es definitiva y no un simple aplazamiento.

    7.2.3. Retraso de red artificial: aplazado

    El documento original permitía fijar un retraso artificial antes de cada respuesta del servidor, para observar el comportamiento de la interfaz en una red lenta (indicadores de carga, desactivación temporal de botones, etc.). Esta funcionalidad todavía no tiene un equivalente en este port.

    7.3. Una nota sobre la metodología utilizada en este documento

    Este documento se redactó basándose por completo en el código que realmente se ejecutó: se probó cada ruta del servidor (incluidos los escenarios de autenticación: inicio de sesión correcto o fallido, acceso sin token, acceso con un rol incorrecto), y cada captura de pantalla del cliente (Capítulo 5) se obtuvo interactuando con la aplicación real en ejecución, mediante un navegador Chromium controlado automáticamente con los datos de demostración del script SQL proporcionado. Este enfoque también permitió descubrir, durante la preparación de este documento, un problema específico del uso de [TypeORM] con columnas calculadas ([@RelationId]), que se señaló y se corrigió en el Capítulo 3, directamente en el código entregado. Esta exigencia explica también por qué las capturas de pantalla de Postman no se simularon: este paso lo dejó el autor del documento, quien las realizó directamente desde su propio equipo de trabajo (véase el Capítulo 1).

    7.4. Para ir más lejos desde ahora

    Mientras se esperan los próximos pasos de este port, el servidor y el cliente incluidos con este documento ofrecen una base lista para usar con la que puede experimentar por su cuenta:

    • agregar un nuevo médico o un nuevo paciente (actualmente, esto solo se puede hacer modificando el script SQL; una ruta llamada /addDoctor, también protegida por [@Roles]('ADMIN'), podría ser un buen primer ejercicio);
    • agregar un tercer rol, o un usuario con varios roles, una oportunidad para evaluar de manera muy concreta el costo de abandonar la simplificación que aporta la columna única [role] (véase el Capítulo 3);
    • modificar la presentación del cliente (colores, diseño) sin cambiar el servidor: una buena manera de comprobar que la arquitectura en capas del cliente funciona como se anuncia;
    • revisar el archivo README de cada carpeta del servidor y del cliente entregados: cada uno explica, en su contexto, el papel de los archivos que contiene.
